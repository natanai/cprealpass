## Confirmed successes worth preserving

### BASE-KEEP-01 — candidate launches and reaches gameplay

The combined pre-REDmod candidate is loadable enough to enter normal gameplay and menus. This proves the current source/package is not failing wholesale at startup.

**Preserve during refactor:** every migration lane must keep an exact-compiling, launchable integrated path rather than replacing all routing at once.

### BASE-KEEP-02 — outer hub identity can be changed natively

The stock outer `CYBERWARE` destination appears as **`BIOLOGY`** on the outer menu hub.

**Preserve during refactor:** Biology should continue to occupy the familiar body/Cyberware destination rather than adding an unrelated top-level menu tile if the native route can remain stable.

### BASE-KEEP-03 — stock body/anatomy shell remains valuable

The central Cyberware fullscreen renders correctly with the native anatomical body, system labels, slot layout, and normal Cyberpunk visual language.

**Preserve during refactor:** the target remains reuse of the native body/anatomy shell, zoom/highlight grammar, and body-system spatial language. The problem is current ownership/mounting, not the existence of the stock shell.

### BASE-KEEP-04 — Mod Settings stack is currently operational

The current framework stack successfully exposes a `REALPASS` settings page with two enabled Boolean controls:

- `Enable RealPass`
- `E3 first-person HUD visuals`

This is evidence that the old provider stack works technically. It is **not** evidence that the stack belongs in the final Biology product.

## Confirmed failures / migration requirements

### NAV-01 — Biology identity is inconsistent across menu layers

**Observed:** the outer hub says `BIOLOGY`, but once inside the shared body fullscreen the native top navigation still says `CYBERWARE`.

**Meaning:** the current implementation changes one menu label seam but not every player-facing navigation surface representing the same destination.

**Target:** ordinary navigation should consistently present the destination as **BIOLOGY**. Cyberware remains available inside Biology as a submode.

**Acceptance:** outer hub, inner top tab/navigation, and adjacent menu surfaces that reference the same destination all present `BIOLOGY` unless a deliberately contextual Cyberware-only vendor surface has a documented reason not to.

### NAV-02 — `BIOLOGY | CYBERWARE` selector is mounted incorrectly

**Observed:** very faint `BIOLOGY` / `CYBERWARE` text appears over/among the native top navigation labels and visually collides with stock text.

**Meaning:** the current selector is an overlay attached to the wrong visual layer/position rather than a stable native body-screen control.

**Target:** a legible, intentional selector inside the body fullscreen that does not overlap the game-wide top navigation.

**Acceptance:** selector has one obvious location, readable contrast, correct focus/click behavior, and no collision at supported resolutions/UI scale.

### BIO-01 — hierarchy is still technically “Cyberware with Biology pasted onto it”

**Observed:** entering `BIOLOGY` opens the normal Cyberware equipment layout. The central content is cyberware slots/items; there is no actual Biology overview owning the body shell.

**Meaning:** the conceptual hierarchy in `docs/BIOLOGY-UI.md` has not yet been realized in runtime.

**Target:** `BIOLOGY` owns the shared body shell; `CYBERWARE` is one internal mode. Biology mode hides/replaces equipment-slot content with body-system nodes backed by authoritative model state.

### BIO-02 — live body state is unavailable in the UI

**Observed:** the bottom status reads:

```text
BODY
Body state is unavailable.
```

**Meaning:** the body screen cannot obtain a usable authoritative Biology state in this live save/session. This is a functional/runtime failure, not merely styling.

**Target:** authoritative body state is available after normal game/save initialization and remains available through menu open/close and save/reload.

**Acceptance:** a clean attended build never reports body state unavailable during an ordinary valid player session unless a genuine fail-closed compatibility condition exists; such a condition must be explicit and actionable in diagnostics.

### BIO-03 — persistent Biology system nodes are absent

**Observed:** no persistent inspectable Biology nodes are visible for modeled physiology/body state. Healthy/quiet state therefore cannot be drilled into.

**Target:** modeled Biology systems remain visible/clickable even when normal. `STABLE` is only an overview summary, never a reason to hide inspection.

**Acceptance:** supported nodes can always be selected and zoomed; deliberate drill-down exposes exact authoritative bars/numbers for testing and player inspection.

### BIO-04 — current body copy is still prose-like and low-value

**Observed:** `Body state is unavailable.` is rendered as explanatory sentence copy at the bottom of the screen.

**Target:** overview language is terse instrumentation (`STABLE`, `THIRST`, `PAIN HIGH`, `UNAVAILABLE` only if truly necessary), while detailed explanations/metrics live at deliberate drill-down depth.

### PRES-01 — E3-inspired first-person HUD recreation is not visibly present

**Observed:** ordinary gameplay still looks substantially like the modern/vanilla HUD rather than the intended red 2018/E3-inspired presentation.

**Important nuance:** this does not mean no HUD code is executing. The health bar is hidden, proving presentation behavior is being touched. It means the recognizable full E3-inspired visual result has not been implemented/activated.

**Target:** when the E3 presentation preference is on, the first-person HUD should visibly and coherently use Biology-owned E3-inspired visual language while retaining the modern scanner/quickhack experience.

**Acceptance:** an attended screenshot should make the enabled/disabled states visibly distinguishable without relying on the health bar alone.

### PRES-02 — E3-inspired NPC nameplates are not active

**Observed by project owner:** NPC nameplates do not display the intended E3-inspired presentation.

**Target:** Biology-owned E3-inspired NPC nameplates work for the intended NPC classes/scan/focus states without importing Project E3 runtime code.

**Acceptance:** attended focus/scan screenshots demonstrate the intended nameplate styling while modern scanner/quickhack behavior remains native.

### PRES-03 — health-bar suppression is active but does not prove the E3 toggle works

**Observed:** the ordinary red player health bar is hidden. Turning `E3 first-person HUD visuals` off did **not** restore it.

Under the current locked Biology presentation goals, barless actor-health presentation is a Biology-wide rule while Biology is enabled, not necessarily an E3-skin feature. Therefore **health-bar restoration is not presently the acceptance test for the E3 toggle**.

However, this observation exposes a real problem: the E3 toggle currently has no clearly demonstrated visible effect because the full E3 HUD and nameplates are absent. Agents must not cite “health bar is hidden” as proof that E3 presentation is working.

**Required resolution:** the presentation lane must make the toggle semantics obvious and testable:

- `E3 visuals = ON` -> recognizable Biology-owned E3-inspired HUD + nameplates;
- `E3 visuals = OFF` -> those E3-specific visual treatments yield to the non-E3 Biology/vanilla presentation;
- Biology's separate barless-health decision follows the canonical product goal unless the project owner later explicitly changes that goal.

### SET-01 — player-facing product identity is still RealPass in settings

**Observed:** Mod Settings shows `REALPASS` and `Enable RealPass`.

**Target:** finished player-facing identity is **Biology**. Transitional internal `RealPass`/`CR*` identifiers may remain until safe to migrate, but the shipped UI/package should not expose the obsolete product name.

### SET-02 — settings provider is functional but architecturally suspect

**Observed:** Mod Settings works, but currently buys the product only a tiny two-toggle surface while bringing the current framework dependency chain.

**Target:** dependency audit decides whether these preferences belong in a Biology-owned surface or whether the provider remains justified. Do not preserve RED4ext/ArchiveXL/Mod Settings merely because this screenshot proves they can render two switches.

## What the screenshots do **not** prove

This baseline does not establish:

- that body/metabolism values are updating correctly behind the unavailable UI;
- that injury/combat/armor models are accepted in live combat;
- that E3 presentation files are entirely absent rather than merely not routed/activated;
- that every menu label is wrong at every resolution;
- that REDmod can or cannot replace each current hook;
- that the master switch fully yields every wrapped system to vanilla;
- that the E3 toggle should restore the health bar while Biology remains enabled. The current locked barless goal says otherwise; the observed problem is that the toggle has no clear visible E3 effect.

Agents must investigate rather than infer those conclusions from screenshots alone.

## Refactor preservation rule

Do **not** patch the old overlay architecture merely to make these screenshots prettier if the same code is about to be replaced by the REDmod-first Biology architecture.

Instead, each issue above is an acceptance requirement for the migration. A migration lane may fix a current implementation directly only when the fix survives into the intended final architecture.
